# 遮挡后的编号关联

原流程虽已按类别分开运行 ByteTrack，但同为“人”的目标仍主要按运动和框重叠匹配。40 秒道路测试片段中，原 46 号红衣行人在约 33 秒与浅色行人交叠后，旧编号接到了浅色行人身上。这是编号关联错误，增加检测框置信度不能直接解决。

## 当前实现

- 行人使用作者发布的 OSNet x0.25 / MSMT17 权重提取衣着与轮廓特征，结合 ByteTrack 的运动匹配及衣着颜色校验。不同类型仍分别跟踪，汽车不运行行人外观模型。
- 高置信度和低置信度关联都经过外观校验，不能让第二阶段绕过校验。
- 检测框互相交叠，或一个框包含两个近期预测位置时，暂停更新外观样本，减少将混合画面学成原人物外观的风险。
- 外观矛盾或交叠时匹配候选过于接近，会拒绝沿用旧编号。之后可能重新编号；没有用预测框填补漏检帧。
- 继续保留当前检测坐标、类别与编号、同类配色、标签避让和按编号选中。

模型在本地 CPU 运行，未调用人脸服务或身份数据库。特征只在单次视觉 worker 中用于当前短片的关联，未写入上传结果、聊天或跨用户检索库。权重及架构校验见 `vision/appearance-model.lock.json`，参数与版本见 `vision/upload-tracking.json`。源码与 MIT 许可保留在 `vision/vendor`。依据作者的[模型发布页](https://huggingface.co/kaiyangzhou/osnet)与[项目文档](https://kaiyangzhou.github.io/deep-person-reid/)准备权重。

## 验证范围

在同一组实际检测结果上对照原关联与新关联，开发助手逐帧核对红衣行人在 20、21.6、24、26、30、32、33.2、33.6、34、34.6、35.4、36.6 秒的位置：原流程在交叠后使用另一个编号，且原编号出现在浅色行人身上；新流程在这 12 个检查点维持同一编号，未接到浅色行人身上。重新分析时编号可能重新分配，对照比较的是画面中的同一行人，而不是编号数值必须相同。

详细结果在 `evals/tracking-stability-spotcheck.json`。这是开发助手对一个已知问题片段的检查，没有独立人工标注或独立测试集，不代表全部人员均无串号。低清、长时间完全遮挡、衣着接近或镜头移动时，仍可能漏检、重新编号或发生关联错误。跟踪记录数仍不能解释为全片唯一人数。

实际通过上传 API 重新处理原片后，这 12 个检查点同样保持一个编号；本机单次完整处理约 47 秒。可在本地结果到期前复查：`python evals/check_tracking_stability.py --result work/uploads/<作业编号>/result.json`。检查器同时核对输入 SHA256，拒绝拿这组位置检查其他视频。

回归覆盖：强、弱置信度候选均不能借用外观明显不同的旧编号；两人交会时不学习混合外观；无法区分的合并框不会强占旧编号；原检测索引仍正确且不重复。部署到新机器需运行 `python vision/download_model.py`，现在会额外准备约 9.3 MB 的外观权重。旧版跟踪结果需要重新上传分析，不与新版补查混用。

## 密集场景的后续修正（2026-11-03）

原有保守规则在密集商业街中会长期过滤起始就被遮挡的目标。`appearance-gated-v2`允许用相邻两帧的严格位置及临时外观一致性确认这些目标，临时外观不进入长期档案、不跨缺帧复用，也不放宽已存在干净档案的限制。新增三类回归覆盖该路径；原红衣行人12个检查点通过真实上传回归。[密集场景的实现、前后画面和限制](crowd-detection.md)。
